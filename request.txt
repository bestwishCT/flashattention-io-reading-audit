009: Abstract
010: Transformers are slow and memory-hungry on long sequences, since the time and memory complexity
011: of self-attention are quadratic in sequence length. Approximate attention methods have attempted
012: to address this problem by trading oﬀ model quality to reduce the compute complexity, but often do
013: not achieve wall-clock speedup. We argue that a missing principle is making attention algorithmsIO-
014: aware—accounting for reads and writes between levels of GPU memory. We proposeFlashAttention,
015: an IO-aware exact attention algorithm that uses tiling to reduce the number of memory reads/writes
016: between GPU high bandwidth memory (HBM) and GPU on-chip SRAM. We analyze the IO complexity
017: of FlashAttention, showing that it requires fewer HBM accesses than standard attention, and is
018: optimal for a range of SRAM sizes. We also extendFlashAttention to block-sparse attention, yielding
019: an approximate attention algorithm that is faster than any existing approximate attention method.
020: FlashAttentiontrains Transformers faster than existing baselines: 15% end-to-end wall-clock speedup
021: on BERT-large (seq. length 512) compared to the MLPerf 1.1 training speed record, 3× speedup on
022: GPT-2 (seq. length 1K), and 2.4× speedup on long-range arena (seq. length 1K-4K).FlashAttention
023: and block-sparse FlashAttentionenable longer context in Transformers, yielding higher quality models
024: (0.7 better perplexity on GPT-2 and 6.4 points of lift on long-document classiﬁcation) and entirely new
025: capabilities: the ﬁrst Transformers to achieve better-than-chance performance on the Path-X challenge
026: (seq. length 16K, 61.4% accuracy) and Path-256 (seq. length 64K, 63.1% accuracy).
027: 1 Introduction
028: Transformer models [82] have emerged as the most widely used architecture in applications such as natural
029: language processing and image classiﬁcation. Transformers have grown larger [5] and deeper [83], but
030: equipping them with longer context remains diﬃcult [80], since the self-attention module at their heart
031: has time and memory complexity quadratic in sequence length. An important question is whether making
032: attention faster and more memory-eﬃcient can help Transformer models address their runtime and memory
033: challenges for long sequences.
034: Many approximate attention methods have aimed to reduce the compute and memory requirements of
035: attention. These methods range from sparse-approximation [51, 74] to low-rank approximation [12, 50, 84],
036: and their combinations [3, 9, 92]. Although these methods reduce the compute requirements to linear or
037: near-linear in sequence length, many of them do not display wall-clock speedup against standard attention
038: and have not gained wide adoption. One main reason is that they focus on FLOP reduction (which may not
039: correlate with wall-clock speed) and tend to ignore overheads from memory access (IO).
040: In this paper, we argue that a missing principle is making attention algorithmsIO-aware [1]—that is,
041: carefully accounting for reads and writes to diﬀerent levels of fast and slow memory (e.g., between fast GPU
042: on-chip SRAM and relatively slow GPU high bandwidth memory, or HBM [45], Figure 1 left). On modern

022: 2 Background
023: We provide some background on the performance characteristics of common deep learning operations on
024: modern hardware (GPUs). We also describe the standard implementation of attention.
025: 2.1 Hardware Performance
026: We focus here on GPUs. Performance on other hardware accelerators are similar [46, 48].
027: GPU Memory Hierarchy. The GPU memory hierarchy (Fig. 1 left) comprises multiple forms of
028: memory of diﬀerent sizes and speeds, with smaller memory being faster. As an example, the A100 GPU
029: has 40-80GB of high bandwidth memory (HBM) with bandwidth 1.5-2.0TB/s and 192KB of on-chip SRAM
030: per each of 108 streaming multiprocessors with bandwidth estimated around 19TB/s [44, 45]. The on-chip
031: SRAM is an order of magnitude faster than HBM but many orders of magnitude smaller in size. As compute
032: has gotten faster relative to memory speed [61, 62, 63], operations are increasingly bottlenecked by memory
033: (HBM) accesses. Thus exploiting fast SRAM becomes more important.
034: Execution Model. GPUs have a massive number of threads to execute an operation (called a kernel).
035: Each kernel loads inputs from HBM to registers and SRAM, computes, then writes outputs to HBM.
036: Performance characteristics. Depending on the balance of computation and memory accesses, op-
037: erations can be classiﬁed as either compute-bound or memory-bound. This is commonly measured by the
038: arithmetic intensity [85], which is the number of arithmetic operations per byte of memory access.
039: 1. Compute-bound: the time taken by the operation is determined by how many arithmetic operations there
040: are, while time accessing HBM is much smaller. Typical examples are matrix multiply with large inner
041: dimension, and convolution with large number of channels.
042: 2. Memory-bound: the time taken by the operation is determined by the number of memory accesses, while
043: time spent in computation is much smaller. Examples include most other operations: elementwise (e.g.,
044: activation, dropout), and reduction (e.g., sum, softmax, batch norm, layer norm).
045: Kernel fusion. The most common approach to accelerate memory-bound operations is kernel fusion: if
046: there are multiple operations applied to the same input, the input can be loaded once from HBM, instead of
047: multiple times for each operation. Compilers can automatically fuse many elementwise operations [53, 65, 75].

032: Theorem 2. Let N be the sequence length, d be the head dimension, and M be size of SRAM with d ≤ M ≤ Nd.
033: Standard attention (Algorithm 0) requires Θ(Nd + N²) HBM accesses, while FlashAttention (Algorithm 1)
034: requires Θ(N²d²M⁻¹) HBM accesses.
035: For typical values of d (64-128) and M (around 100KB), d² is many times smaller than M, and thus
036: FlashAttentionrequires many times fewer HBM accesses than standard implementation. This leads to
037: both faster execution and lower memory footprint, which we validate in Section 4.3.
038: The main idea of the proof is that given the SRAM size of M, we can load blocks of K, V of size Θ(M) each
039: (Algorithm 1 line 6). For each block ofK and V, we iterate over all blocks ofQ (Algorithm 1 line 8) to compute
040: the intermediate values, resulting in Θ(NdM⁻¹) passes over Q. Each pass loads Θ(Nd) elements, which
041: amounts to Θ(N²d²M⁻¹) HBM accesses. We similarly prove that the backward pass of standard attention
042: requires Θ(Nd + N²) HBM accesses while the backward pass of FlashAttention requires Θ(N²d²M⁻¹)
043: HBM accesses (Appendix B).
044: We prove a lower-bound: one cannot asymptotically improve on the number of HBM accesses for all
045: values of 𝑀 (the SRAM size) when computing exact attention.
046: Proposition 3. Let 𝑁 be the sequence length, 𝑑 be the head dimension, and 𝑀 be size of SRAM with
047: d ≤ M ≤ Nd. There does not exist an algorithm to compute exact attention with o(N²d²M⁻¹) HBM accesses
048: for all M in the range [d, Nd].
049: The proof relies on the fact that for M = Θ(Nd) any algorithm must perform Ω(N²d²M⁻¹) = Ω(Nd)
050: HBM accesses. This type of lower bound over a subrange of𝑀 is common in the streaming algorithms
051: literature [88]. We leave proving parameterized complexity [27] lower bounds in terms of𝑀 as exciting future
052: work.
053: We validate that the number of HBM accesses is the main determining factor of attention run-time.
054: In Fig. 2 (left), we see that even thoughFlashAttentionhas higher FLOP count compared to standard
055: attention (due to recomputation in the backward pass), it has much fewer HBM accesses, resulting in much
056: faster runtime. In Fig. 2 (middle), we vary the block size𝐵𝑐 of FlashAttention, which results in diﬀerent
057: amounts of HBM accesses, and measure the runtime of the forward pass. As block size increases, the number
058: of HBM accesses decreases (as we make fewer passes over the input), and runtime decreases. For large enough
059: block size (beyond 256), the runtime is then bottlenecked by other factors (e.g., arithmetic operations).
060: Moreover, larger block size will not ﬁt into the small SRAM size.
